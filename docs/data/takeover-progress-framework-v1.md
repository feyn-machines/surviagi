## 1. 分开三个问题

| 问题 | 记录内容 | 与计分的关系 |
| --- | --- | --- |
| 这条材料和事件从哪里来？ | 来源身份、原始链接、作者、时间、事件记录状态 | 建立可追溯事件，区分官方发布、具名讲话和社区反应 |
| 其中的能力宣称是否成立？ | 厂商自述、独立支持、存在争议、尚未验证 | 单独展示；不把真假判断当作热度乘数 |
| 事件产生了多少可观察反应？ | 帖子数、点赞、转发、回复、独立账号、社区分布、计数快照 | 用来计算声量、互动、参与和传播信号 |

例如“某公司宣布某模型具有一项能力”，可以确认公告确实存在，同时把能力效果记为厂商自述。即使效果尚未独立验证，也可以记录公告的传播和讨论；高互动本身不会把能力宣称变为已验证事实。

“支撑事件存在的原始证据”与“支撑事件显著程度的社交信号”使用不同记录。反对、质疑和争议也会产生互动，不能把互动数叫作支持人数。

## 2. 第一版实际取得什么

本次只做过去 24 小时的小样本字段探测，不导入生产事件：

| 数据 | 代码与小样本结果 | 首版处理 |
| --- | --- | --- |
| X 帖子、作者、时间、正文、引用关系 | 现有采集器已保留 | 事件锚点、关联搜索、去重与账号统计 |
| X 点赞、转发、回复、引用计数 | 原始响应中 3 条样本均返回；现有标准化器尚未保留 | 增加字段保存后作为互动快照 |
| X 收藏计数 | 3 条原始样本返回 | 可选辅助项 |
| X 浏览量 | 本轮 3 条原始样本均未返回 | 可选，缺失为未知，不作为必需项 |
| Reddit score、评论数、赞同比例 | Arctic 返回的 3 条样本均有；现有代码已保存 | 保留平台原值及提供方，不把 score 改叫点赞数 |
| Reddit 社区、作者、帖子时间与正文 | 现有标准化代码保留 | 社区分布、观察到的账号数和讨论主题 |
| 评论正文、评论作者 | 当前 Reddit 采集流程只取帖子，不取评论正文 | 不能据评论计数声称分析了所有评论或参与者 |
| 互动增速 | 尚未核验同一帖子的持续刷新 | 等重复快照和时间有效性验证后启用 |

X 原始响应有 3 条对象，现有精确时间窗过滤后保留 2 条；本轮计数均为 0。这证明样本中的字段存在，不能推断全平台字段覆盖或计数质量。

Reddit 当前代码把缺失的 score 和评论数转成 0，必须在计分接入前修正。归档提供方的计数可能有自己的更新时间；取得材料的时间不能冒充计数实际刷新时间。上述检查没有修改采集器代码。

## 3. 指标先从原始字段派生

| 指标 | 计算输入 | 结果的准确含义 |
| --- | --- | --- |
| 声量 | 与事件相关、去重后的帖子 ID 数 | 在声明的查询范围内观察到多少条相关内容 |
| 互动热度 | X 点赞／转发／回复／引用；Reddit 评论数与平台 score | 各平台返回的互动信号，保留分项 |
| 参与广度 | 去重后的可识别作者账号 | 观察到多少个发声账号；不是全网参与人数，也不是跨平台去重的人数 |
| 社区扩散 | 涉及哪些被跟踪的 subreddit、各社区帖子分布 | 在已查询社区内传播多广 |
| 变化速度 | 同一帖子、同一指标在两次可用快照中的差值／时间 | 返回计数的变化；不自动等同新增独立用户 |

核心输出先保留这组信号向量，不凭想象填平台没有返回的数据。正文可用于标注“分享、体验、质疑”等讨论类型，但那是文本分析结果，要与原始计数分开。

## 4. 事件与反应怎样关联

官方公司／产品账号继续作为事件的主要入口。围绕已建立的事件，用产品名、版本名、原帖链接和引用关系建立相关讨论搜索；匹配规则与查询词留档。

搜索命中先做相关性筛选，再连接到事件。标签可以多选，但每条用于计分的关系需要明确指向事件和赛道。宽泛出现“AI”的帖子不能自动分配给所有事件。

同一原帖由多个查询命中，只保留一个帖子实体和多条采集记录；原生转发包装与被转发原文要避免重复计数。多家账号报道同一次发布仍归到一个事件。讨论跨多个事件时，关联可以多对多；计分时使用明确分配份额，不能给每个事件都无条件记满。

来源角色分开保存：官方事件锚点、当事人陈述、独立讨论、转载／引用。社区账号不因为参与讨论就自动成为官方来源。

## 5. 怎样归一化与累计

### 先记录可直接计算的量

立刻可定义：去重事件累计、各赛道事件数、观察到的相关帖子数、互动分项、发声账号数和社区分布。这些都有明确的输入和计算口径。

第一版不再使用“自主性 3 级”“稳定性 4 级”作为每日人工评分。深层能力与实际应用材料仍可保留，作为后续解释或新增指标，不能卡住当前信号采集。

### 再建立固定评分口径

非负计数可先用 `log(1+x)` 缓和极大值的影响；有正负的平台 score 保留原值，可另用带符号的对数转换。转换不能把缺失变为 0。

归一化要在相同平台、指标、事件／帖子观察年龄窗口和采集范围内比较。X 点赞与 Reddit score 不直接相加；发布时间相差数日的累计互动也不直接当成同龄表现。

**社交热度目前没有足够的连续同口径样本，先不拍定其权重或互动满分上限。** 从实际启用日积累样本后，冻结参考分布、指标集合和权重。本层冷启动展示原始信号与覆盖；v0.3 的能力进度可以独立建立带明确标注的 AI 估计基线，不必等待热度校准。

缺某项指标时保留未知；只做 X 的观察配置可以单独运行。混合平台配置需要明确哪些字段与来源是必需的，不能某周缺 Reddit 就偷偷把其余权重放大。

### 事件贡献与赛道累计

评分口径冻结后的计算合同是：

```text
事件贡献 = 该事件的信号分 × 分给该赛道的份额
赛道累计 = Σ 每个去重事件的当前贡献
本次账本更新 = 该事件的新贡献 − 已记入的旧贡献
```

同一个事件分给所有计分赛道的份额之和为 1；暂未归类的份额留在“未分类”。多标签用于检索，不能让总分因打了更多标签而膨胀。

例如，一条事件的贡献从 8 变为 11，本次只增加 3；不能每天重新把 8、9、11 全部再加一遍。标签或归属修订也通过差额账本调整，不创造新的事件贡献。

本观测层分别保存**累计事件信号贡献**和**最近窗口热度**。它们本身没有“世界已完成接管”的终点，不能通过任意压缩公式变成完成百分比。真正的 0–100 接管进度，由 v0.3 的固定世界范围、权重与 AI 能力状态估计计算。

## 6. “接管进度”怎样保留解释力

产品核心采用 v0.3 的“AI 接管进度估计”；事件与社区信号作为可追溯输入，另外展示：

- 哪些赛道持续出现重要事件，累计贡献怎样变化。
- 哪些事件正在获得讨论，关注来自哪些账号和社区。
- 本周贡献变化来自新事件、已有事件互动变化，还是采集范围／归属修订。
- 每个值对应的事件、原始数据、采集时间和计算版本。

事件类型保留发布、开放、部署、人物判断、限制、撤回等。撤回、争议或事故的热度可以很高，展示为相应类型的事件信号，不能自动解释成正向能力推进。方向判断不从点赞正负或情绪直接推导。

同样，真实性状态变化不能删除已经观察到的关注；它应更新事实说明与解释。若后来证实关联错了或计数无效，则作为数据更正重算，而不是说世界在这一天发生了相应能力变化。

这些连续的赛道归属、事件贡献账本和可追溯解释构成核心产品；原始新闻列表只是输入的一种查看方式。

## 7. 原始数据合同

每个计数保存：平台、提供方、帖子 ID、所属事件、帖子发布时间、采集时间、提供方可用的计数更新时间、计数原值、字段是否存在、查询轮次及范围。

对同一帖子追加快照，不覆盖旧值。相同平台与 ID 去重，保留多次取得记录。提供方未说明计数更新时间时保持未知；尚未证明能够刷新时，不计算增速或宣称实时热度。

声量和社区广度必须携带：查询词版本、查询的账号／社区、时间窗、页数与条数预算、是否取尽分页、错误和截断状态。达到条数上限表示样本受限，不能当成全网总声量。

## 8. 不回溯；社区以后补录

保持“从实际启用日起采集新材料”的范围。以前的材料可以由社区将来提交原始链接、发生时间、事件描述和赛道归属，再审核合入。

社区补录事件与抓取社交平台的“社区讨论指数”是两件事：前者补证据和历史时间线，后者统计外部可观察信号。自己社区的投稿量和点赞量不自动增加事件真实性。

历史事件发生时间与投稿／补录时间分别保存；今天取得的互动快照不能倒填成事件发生当周的热度。已发布周报保留版本，补录和更正单列。

## 9. 当前可实施的下一层

1. X 标准化器保留已实测返回的互动字段；Reddit 保留缺失与 0 的区别。
2. 加入计数快照、查询范围、提供方与新鲜度记录。
3. 为官方事件建立相关讨论采集与去重，输出声量／互动／参与／社区分布。
4. 从启用日开始积累样本，再冻结归一化参考和权重，启用事件贡献与赛道累计。
5. 将周报建立在指数分解、原始指标变化与事件解释上。

不要求为每条事件补齐实验评测、实际替代率或人工四级评估。当前确认的是字段可取得及框架合同；还没有一套已运行的接管评分引擎。

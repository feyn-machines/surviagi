# 登录、帐号提交、订阅与管理员后台设计

日期：2026-10-04。状态：方向由用户在 2026-10-04 的对话中确认，本文待用户审阅。它在 [服务器数据库与数据发布设计](2026-10-03-server-database-and-data-releases-design.md) 预留的"用户数据 `app`"位置上实施第一批用户功能。

## 用户的决定（2026-10-04）

1. 增加登录、让用户提交需要监控的帐号（公司或个人）、管理员后台。
2. 提交入口放在「声音」页，那页已经分成人物和公司。
3. 管理员后台第一版只审核提交。
4. 申请不公开，只有提交者本人和管理员可见。
5. 增加订阅：订阅本网站的更新和周报，记录基本信息。
6. 订阅要求先登录。

这取代了项目说明中"登录只用于获取 Agent 上报的 API Key；不设编辑或管理员角色；没有其他用户用途"的规则；`CLAUDE.md` 同步更新。Google 登录用 Better Auth 的既有决定不变。

其余内容是本文提出的设计。

## 不变的边界

- 采集和处理只在本机运行。网站请求不触发抓取。
- 知识数据 `kg` 仍按版本发布，网站对它只读。数据发布不读写 `app`。
- 帐号的名单状态只由本机的检查日志推导。后台"通过"不等于身份已确认。
- 不登录可以浏览全站。爬虫看到的页面内容不因登录功能改变。
- 英文和简体中文完整提供；界面文案是短标签和数字。

## 登录

- Better Auth，Google 登录，会话存数据库。凭据是 `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`，加一个会话密钥；本机在 `.env`，服务器在 `site.env`，都不进 Git。
- 页头右侧"登录"按钮；登录后显示头像，菜单里有"退出"，管理员多一项"后台"。
- 登录状态由浏览器端取得并渲染，页面的服务端输出对所有访问者相同。
- 登录后回到原来的页面和语言。
- 只保存 Google 返回的邮箱、名字、头像。没有个人资料页和注册表单。
- 没有配置登录凭据或没有数据库时（本机文件模式、CI），登录按钮不显示，提交和订阅入口不显示，其余页面照常。

## 提交监控帐号

入口：声音页"人物""公司"两栏标题旁各一个"提交帐号"按钮。类型由所在栏目决定。未登录时先去登录，回来后回到该栏目，再点一次按钮打开表单。

表单：

| 项 | 规则 |
| --- | --- |
| X 帐号 | 必填。接受 `@name`、`name`、`https://x.com/name`、`https://twitter.com/name`；规范化为不带 `@` 的用户名，1 到 15 位字母、数字或下划线，比较时不分大小写 |
| 理由 | 选填，最多 280 字，按纯文本保存和显示 |

提交结果：

| 情况 | 结果 |
| --- | --- |
| 帐号已在当前生效数据的名单里 | 提示"已在监控"，不生成申请 |
| 本人已提交过这个帐号 | 显示那条申请的状态，不生成新申请 |
| 本人待审核的申请已有 10 条 | 拒绝，提示上限 |
| 其他 | 生成一条待审核申请 |

"我的提交"：声音页上只对本人显示的一块，列出帐号、类型、状态（待审核、已通过、已拒绝）、拒绝原因、时间。

申请的状态只有三种：`pending`、`approved`、`rejected`。这是申请流程的状态，不是知识数据的概念，定义在 `app` 的表结构里；帐号类型沿用本体中已有的 `person`、`organization`。

## 订阅

- 入口：页脚的"订阅"按钮，以及登录菜单里的"订阅"。未登录时先去登录。
- 两类，可分别勾选：网站更新、周报。
- 记录：用户（邮箱和名字来自登录）、订阅时的界面语言、订阅了哪几类、订阅时间、退订时间。
- 可随时在同一处退订，退订保留记录并写入退订时间。
- 本版只收集名单，**不发送任何邮件**。发信服务、域名发信验证、邮件里的退订链接，随周报一起另行设计。

## 隐私说明与服务条款页面

Google 要求登录应用在品牌页面填好应用首页和隐私权政策链接后才能发布为正式版（2026-10-04 在 Google 后台确认："如需发布应用，您必须在品牌页面中完成配置"）。因此本次一并加两个页面，中英文各一份：

- `/privacy`：保存哪些信息（Google 邮箱、名字、头像；提交的帐号和理由；订阅类别和语言）、用途、不出售不共享、保存位置、如何退订、如何要求删除（联系邮箱）。
- `/terms`：提交内容的规则（只提交公开的 X 帐号、不得冒名或骚扰）、申请可能被拒绝、数据为机器提出且未经审核、服务按现状提供。

两页进站点地图，页脚有链接。正文需用户过目后才上线。

上线顺序因此是：页面先随代码发布上线 → 用户在 Google 品牌页面填入两个链接 → 点"发布应用"。在此之前应用处于"测试"状态，只有加入测试用户名单的邮箱能登录，足够开发和验收使用。

## 管理员后台

- 地址 `/admin`（中文 `/zh-CN/admin`）。不进站点地图，`robots.txt` 禁止，页面带 `noindex`。未登录或非管理员访问返回 404。
- 管理员名单存在数据库表 `app.admins` 里（用户 2026-10-04 决定：写到库里，部署时自动带上去）。名单的来源是本机被忽略的 `.env` 中的 `ADMIN_EMAILS`（逗号分隔）；`pnpm db:setup` 和本机的 `pnpm app:setup` 每次运行都把表同步成这份名单（多的删、少的加；名单为空时拒绝同步，表不变）。邮箱不写进 Git（仓库是公开的）。判断管理员时比较不分大小写，且该 Google 邮箱须已验证。改名单不改代码，也不用重新发布网站。
- 权限在服务端每次请求时检查；界面上隐藏入口不算权限控制。
- 申请列表：
  - 待审核在前，可切换查看已处理的。
  - 同一帐号、同一类型的多条申请合并成一行，显示提交人数和各自理由。
  - 每行有到 X 主页的链接。
  - 操作：通过；拒绝（必须填原因，最多 280 字）。对合并行的操作作用于其中所有待审核申请。
  - 已处理的申请显示处理人和时间，不能再改。
- 订阅：显示总人数和两类各自人数；可下载名单（CSV：邮箱、名字、语言、类别、订阅时间）。

## 数据

服务器数据库新增结构 `app`：

- Better Auth 的表：用户、会话、第三方帐号、验证。
- `app.submissions`：编号、用户、平台（`x`）、规范化后的用户名、类型、理由、状态、处理人、处理原因、处理时间、创建时间、导入本机的时间。同一用户对同一平台和用户名只能有一条。
- `app.admins`：管理员邮箱（小写）、加入时间。
- `app.subscriptions`：用户、类别（`updates`、`weekly`）、语言、订阅时间、退订时间。同一用户每类一条。

数据库身份：

| 身份 | 权限 |
| --- | --- |
| `oaw_site`（已有） | 只读 `kg` |
| `oaw_app`（新增） | 读写 `app`，不能访问 `kg` 的写入 |
| `oaw_kg_writer`（已有） | 写 `kg`，不能访问 `app` |

网站用两个连接：读知识数据的沿用 `DATABASE_URL`，用户数据用 `APP_DATABASE_URL`。口令在服务器上生成，写入权限为 600 的 `site.env`，不进 Git、不打印。

结构变更放在 `db/app/` 下按编号的文件里，由 `pnpm db:setup` 应用（可重复执行）。

备份：服务器上每日对 `app` 做一次 `pg_dump`，保留 14 天，放在 `/opt/openaiwill/backups/`。知识数据可从本机重新发布，不备份。

## 与本机采集的衔接

- 新命令 `pnpm submissions:pull`（本机运行，经 SSH 转发）：读取"已通过、尚未导入"的申请，写成本机被忽略目录 `data/` 下的一份清单（用户名、类型、理由、提交人数），并在服务器上回写导入时间。重复运行不会重复导入。
- 清单进入现有的名单导入流程。个人帐号需要补上人物姓名和角色后才能导入为候选，这一步在本机完成，不在网站上。
- 之后是现有流程：身份检查、启用采集、处理、数据发布。帐号出现在公开的声音页，是数据发布的结果。
- 申请的"已通过"不随后续结果变化；身份检查没通过的帐号不会出现在公开名单里，提交者看到的仍是"已通过"。

## 请求与安全

- 提交、订阅、审核都经服务端处理，校验登录、校验输入、校验来源（防跨站请求），不信任浏览器传来的用户或类型以外的字段。
- 用户填写的文字按纯文本转义输出。到 X 的链接由规范化后的用户名拼出，不使用用户提交的原始链接。
- 提交数量限制：每人最多 10 条待审核；每人每小时最多 20 次提交请求。
- `/api/auth/*`、`/admin`、用户数据接口的响应带 `Cache-Control: no-store`。
- 登录凭据、会话密钥、数据库口令只在环境文件里，不带 `NEXT_PUBLIC_` 前缀。

## 发布

这是一次代码发布加一次数据库结构升级，不需要数据发布：

1. `pnpm db:setup`：建 `oaw_app` 身份和 `app` 结构，往 `site.env` 写入 `APP_DATABASE_URL` 和会话密钥，装每日备份。
2. 把 `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`ADMIN_EMAILS` 写入服务器的 `site.env`（经 SSH，不经过 Git，不打印）。
3. `pnpm site:release`，候选检查通过后 `pnpm site:promote`。

需要用户做的：

- 在 Google 后台为该登录应用登记回调地址 `https://openaiwill.com/api/auth/callback/google`，本机调试另加 `http://localhost:3456/api/auth/callback/google`。
- 管理员的 Google 邮箱已由用户提供，记在本机 `.env`。
- 开发期间把自己的 Google 邮箱加入该应用的测试用户名单；两个页面上线后在品牌页面填入 `https://openaiwill.com`、`https://openaiwill.com/privacy`、`https://openaiwill.com/terms`，再发布应用。不上传徽标（上传会触发品牌验证）。

## 验证

- 单元测试：用户名规范化（各种写法、非法输入）、管理员判断、提交结果的四种情况、数量限制。
- 真实数据库测试（本机 PostgreSQL）：`app` 结构可重复应用；同一用户重复提交被拒；合并行的审核作用于所有待审核申请；已处理的不可再改；`oaw_app` 写不了 `kg`，`oaw_kg_writer` 读不了 `app`；`submissions:pull` 重复运行不重复导入。
- 页面检查：未登录和非管理员访问 `/admin` 得到 404；`/admin` 不在站点地图里；没有登录配置时站点照常构建和运行；中英文、桌面和手机宽度下的页头、声音页、页脚。
- `pnpm check` 全部通过。

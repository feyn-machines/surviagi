# 证据名单、热度与第三方验证机制

日期：2026-09-23 · 状态：已确认方向（用户 2026-09-23：「不用我审核，你直接来，最后这些都要有机制」）

问题：710 条证据里 690 条是厂商自证，没有一条第三方验证；社交媒体只用了官方账号的正文，互动数据和非官方账号都没进入计算。这份规格把「谁的帖子算什么证据、什么时候去找第三方、热度怎么算」全部定成规则，由流水线执行，不靠人工逐个审定。

## 1. 对象

落在 `2026-09-12-postgresql-business-schema-design.md` 第 6 节已经设计、尚未建表的三张表上，另加一张检查日志：

| 表 | 作用 |
|---|---|
| `people` | 人物，身份出处 URL |
| `person_affiliations` | 人物与机构的关系（雇员 / 创始人 / 投资人 / 顾问 / 合作 / 学术），带生效和结束时间、出处 |
| `source_accounts` | 平台账号：平台稳定 ID、handle、归属人物或机构、名单角色、名单用途、名单状态 |
| `source_account_checks` | 每一次身份、任职、活跃度检查的结果和依据，只追加不修改 |

状态由检查日志推导，不手工改。

## 2. 不给账号分用途，只看帖子（用户 2026-09-23 修订）

账号不再分「验证 / 印证 / 热度」。每条帖子按它自己说了什么判断，并挂到**事件**和**上游帖子**上：

- **帖子 → 上游帖子**：回复、引用、转发，都是原始数据里的事实。
- **帖子 → 事件**：从事件的官方原帖出发，沿回复、引用、转发链归属；没有上游关系、但在 7 天内提到产品名的，记为「提及」，交判官确认。
- **帖子的证据层级**只看帖子性质和作者独立性（rule:verification-tier）：亲手测试、独立评测、本机构生产使用 → T1；专家评估 → T2；观点、转述、无关 → 不产生证据；转发没有自己的内容，只算热度。
- 帖子性质还限定它最多能证明到哪一级（rule:nature-caps-level）：L4 要求已在真实业务中运行，只有生产使用能证明。

账号上保留的只有：身份（是不是本人）、任职（用于独立性）、是否被剔除（营销号）。`panel_role` 只作描述。

原「按用途分组、连续 5 次无产出降级」的规则已删除：首次试跑中它把 139 个验证账号降为印证，而一个账号没谈某个产品是常态，不说明它不可靠。

## 3. 生命周期

`candidate 候选 → identity_confirmed 身份已确认 → enabled 启用`，另有 `suspended 暂停`、`retired 退出`。

| 转换 | 条件（全部来自检查日志） |
|---|---|
| 候选 → 身份已确认 | 平台稳定 ID 已解析，且 handle 有一手依据（本人主页、GitHub、机构官网链接到该账号）或本人简介依据 |
| 身份已确认 → 启用 | 未被剔除；最近一次任职检查不超过 120 天；最近 180 天内有发帖（尚无活跃度数据时暂视为满足，首轮采集后复核） |
| 启用 → 暂停 | 90 天没有发帖；handle 指向了另一个平台 ID；任职检查过期；身份检查失败 |
| 暂停 → 启用 | 导致暂停的条件消失 |
| 任意 → 退出 | 账号注销，或连续两次复核失败 |

只有第三方名单依据、没有一手依据的账号停在候选，直到补到依据。

## 4. 独立性：按公司判断，按时间判断

一条名单帖子谈的是机构 X 的产品：

- 帖子发布时，账号在 X 有有效的雇员、创始人、投资人、顾问或合作关系 → 厂商自证（T3）；
- 否则，按判官对帖子性质的判断：亲手测试或独立评测 → 第三方验证（T1）；采用方谈本机构生产使用 → T1；有依据的专家评估 → 多方印证（T2）；观点或转述 → 不产生证据。

任职变动带生效日期，所以同一个人在加入某公司前后的帖子，会自动得到不同判断。

## 5. 何时去找第三方（触发阈值）

一条更新同时满足以下两条才触发查询，不做大范围搜索：

1. **有被压低的声明**：至少一条证据「原文说到」的级别高于「我们记为」的级别。只有这种情况第三方验证才会改变结果。
2. **足够重要**：热度（第 7 节）位于采集窗口内前 20%，或更新类型是版本发布、能力更新、评测结果。

触发后，只查启用状态、用途为验证或印证的账号，在更新发布后 7 天内、提到该产品的帖子。查询遵守采集器的限速与登录规则。

## 6. 名单自我维护

- **身份**：本人主页、GitHub 或官网链接到账号为一手依据；账号自己的资料显示名一致且简介提到已记录的任职机构，视为本人简介依据（rule:identity-from-profile）。
- **任职**：每 120 天复核；资料快照中简介变化时自动送回复核，已启用账号在复核前暂停。
- **发现**：在事件关系链中反复出现、给出具体测试结果但不在名单里的作者，进入候选，仍须走第 3 节的身份规则。

## 7. 热度

来自已采集的互动快照（`collected_captures.metrics`），与级别完全无关（项目规则：点赞不能加能力分）。

- **每条帖子只采两次**：首次发现一次，发帖后第 7 天一次作为定稿（用户 2026-09-23 确认）。互动大多发生在前两天，第 7 天基本定型；每天回看同一帖子只增加请求。
- 排名用**互动量**（点赞 + 转发 + 引用 + 回复），不用浏览量：按浏览量排时前十全是付费推广帖。同时保留相对该账号中位互动量的倍数和原始浏览量。
- 不满 7 天为**暂估**：页面可展示并标注，不参与定稿排名，不触发验证。
- 事件热度取其互动最多的来源帖子；一条帖子同时宣布多件事时，记下被几个事件共用，排名时只算一次。缺失为空，不当作 0。
- 用途：首页关键事件、「火热的赛道」、第 5 节触发阈值。

## 7.1 采集节奏与账号分工

| 采集 | 对象 | 时机 |
|---|---|---|
| 新帖 | 官方号 51 个；名单中评测者、采用方、实测者、研究者（约 216 个） | 每天 |
| 定稿快照 | 上述帖子 | 发帖后第 7 天 |
| 回复 | 热度前 20% 的帖子与触发验证的更新 | 第 7 天，与定稿同一次 |
| 第三方验证搜索 | 触发的更新 | 第 7 天热度定稿后 |
| 用户资料 | 官方号与已启用的验证、印证账号每周；其余名单账号每月 | 定期 |

- 名单账号不只是被动核对的对象：评测者和采用方**自己产生事件**（评测结果、生产使用），与官方号并列作为事件来源。进入判官前先用跟踪的产品与机构名称做无成本预筛。
- 普通用户的回复只算热度与反应，不算证据；原文只留本机，发布只含统计。反复给出具体测试结果的回复者进入名单候选（第 6 节「发现」）。
- 用户资料中的**简介变化**触发该账号的任职复核；handle 变化按平台 ID 识别。
- **采集一律走项目爬虫 `scripts/crawler/`**（见 `docs/development/x-crawler.md`），不用已退役的 `social-qingguo-collector` 技能。爬虫从账号池（`data/secrets/x-accounts/pool.json`，当前 31 个可用账号）租用账号：限流进冷却、换号重试，认证失败标记失效，传输错误换新连接；每个账号绑一条独占连接即一个稳定出口 IP。
- 名单账号由爬虫直接从 `source_accounts` 读取（`pnpm crawl timeline --targets panel`；2026-09-28 起不再导出清单文件，官方号也已入表），读**账号时间线**，不用搜索接口（诊断期间搜索接口返回 404，时间线保持 200）。
- 第三方验证不做 X 搜索：在已入库的名单帖子里，本地匹配「更新后 7 天内、提到该产品」的帖子，再交判官。
- 估算：日常约 350 次 X 请求（约 7 个限流窗口，一天 96 个），新增约 1,000 条帖子，预筛后约 100–200 条进入判官。

## 8. 系列

同一 `subject_key` 的更新在页面上显示为一个系列（如「GPT-6 Astra 系列 · 11 条」）。只影响展示，不合并事件、不移动证据。

## 9. 同批修正的级别规则

- 非技术障碍不再把环节压成 L0，而是把可记级别上限定为 L3（必须有人在场、签字或担责，到不了无人交付）；障碍作为单独标签展示。
- 判官分数低于 1 的证据不构成级别，只保留作记录；只有这类证据的环节为「证据不全」。

## 10. 执行顺序

1. 建表、导入名单草稿、实现生命周期规则（本地，无外部请求）。
2. 级别规则修正（第 9 节），重新发布。
3. 热度与系列，发布并接到首页原型。
4. 解析名单账号的平台稳定 ID。2026-09-23 已用旧技能解析 214 个（其作者 ID 字段可信）；其余 76 个待爬虫增加「按 handle 查用户」能力后补全。
5. 触发式第三方判定：名单时间线经爬虫采集入库后，本地匹配并交判官（判官调用）。
6. 名单账号时间线纳入每日采集与事件抽取（含预筛）；第 7 天定稿快照、回复采集；采集器用户资料模式与简介变化触发任职复核。

## 11. 不在本规格内

- 微博、公众号等其他平台（中文实测者大多在那里），另行决定采集范围。
- 判官改成选择题与多次判定（用户 2026-09-23：先不重跑）。

## 实现后的变更

- **2026-10-16 印证读数随数据发布**：帖子级印证（`verification_evidence`）一直参与工作级别的计算，但没有发布，导致一项工作页面显示 L3、列出的证据最高只有 L2。现在发布快照在被印证的那条证据上加 `confirmations` 字段（账号、帖子链接、帖子时间、帖子性质、证据档、判官读数和封顶后的级别），筛选条件和封顶与级别计算完全一致。没有被印证的证据行不带这个字段，内容不变；旧版网站代码会忽略这个字段，所以数据可以先于代码上线。工作页、赛道页、职业页和它们的 Markdown 副本都列出这些印证。

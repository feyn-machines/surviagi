# 事件的表达与人物帖子的提取

日期：2026-10-07。状态：已实现；下面“实现后的变更”一节记录与正文不同之处，以该节为准。

## 实现后的变更（2026-10-07，均为用户当天的决定或验证中的发现）

- **转述**：转述帖不产生更新。它转述的是一条已知的公司更新时，由程序按对象名挂到那条更新上，算作“又一个账号这么说”；否则丢弃。名单角色为“转述”的账号、任职于注册公司而复述公司说法的人、复述注册公司对自家产品说法的其他人，都由程序判为转述（`rule:relays-are-not-a-source`）。正文第 4 节“转述只能丢弃或挂靠补充细节”的写法被它取代。
- **平台不做验证**。挂靠只记录“这个账号这么说了”，不评判对错。
- **活动公告停用**：`event_announcement` 标 `until: 2.0.0`，旧行保留，新提取不再产生（迁移 037）。
- **官方账号和其他账号分开提取**，各用一份说明；官方账号的说明里没有“转述”这个概念。一条更新只要有官方来源，行动者就是官方账号。
- **不同人的帖子不合并成一条更新**：各人的实测各算各的。
- **挂靠目标的校验**：模型抄回的标题必须是该更新的标题；帖子正文要出现该更新对象名里的词；官方账号只能挂本公司的更新。
- **非官方账号的帖子归不进任何类型时丢弃**，不保留为“无法分类”。
- **按搜索采集**（`pnpm crawl search`）和 `rule:search-finds-candidates`：搜索到的、名单之外的作者，帖子产生更新时登记为候选账号（迁移 038）。
- **提取归档保存模型的原始输出**（`model_output`），程序规则变了可以重新组装。
- **验证**：2026-09-29 至 2026-10-07 按新版本重抽，共五轮；最后一轮的归档在 `data/extraction/v220-*.json`，之前各轮在 `v220-round1` 至 `v220-round4`。
- 正文第 11 节的五点待确认事项，用户未提出异议，按原方案实现。

## 1. 用户的决定

2026-10-06 至 10-07 的对话中，用户定下：

- 线上的人物帖子有大量无关信息，不应发布。只发布和事件有关联的帖子。
- 事件不只来自官方账号：人物帖子也可以产生事件（方案 B），也可以挂到已有事件上，包括历史事件。
- 事件类型、属性、关系的表达不足，要补。
- 本体和数据增量更新：新版本从某次提取开始生效，不回顾、不重抽全部数据；失效的属性关系就失效，新增的就新增。
- 转述别人消息的帖子不算事件来源。
- 个人开发者发布自己的工具算事件，但帖子要有具体功能或数字。
- 提取每批只跑一次，不做两遍一致性检查。
- 帖子挂到事件时不记角色；作者就是行动者时由程序填写，不让模型写。
- 当前集中于提取。不做重要度之类的 AI 判断指标，不加 Jev 的相关性判断。

未由用户说明、由本文假定的内容，集中列在第 11 节。

## 2. 现状

- 事件只从官方账号帖子提取，全部归到 13 家公司。人物帖子没有进入提取。
- 提取器此前只读 280 字符的摘要。2026-10-07 已改为读完整正文（提示词标记 `deepseek-events-3`）。
- 事件只有标题和一句摘要，没有数字、范围、依据。
- 事件类型词表 `event_kind` 2.0.0 有 15 种，全部是厂商的发布动作。
- 事件的行动者只能是公司：数据库约束要求新词表下的事件必须有 `primary_org_id`。
- 人物帖子只靠结构关系（回复、引用、转发官方帖子）或“事件后 7 天内提到产品名”挂到事件上，内容没有被读过。23,888 条人物帖子里 958 条有关联。
- 发布规则是每个账号取最近 3 条原创帖，没有相关性筛选。线上 623 条人物帖子里 38 条和事件有关联。
- 每条事件带 `kind_vocabulary` 标记，记录它按哪一版词表分类。这是本文推广的增量做法的先例。

## 3. 试验依据

正式设计之前做了三轮试验，都不写数据库。输入是 2026-10-05 全天的 353 条原创帖（人物 307 条、机构 46 条），读完整正文。

| 项目 | 结果 |
| --- | --- |
| 人物帖子的去向 | 22 条产生新事件，10 条挂到已有事件，275 条丢弃 |
| 机构帖子的去向 | 10 条产生新事件，8 条挂到已有事件，28 条丢弃 |
| 事实的原文引用 | 48 条全部能在帖子里逐字找到 |
| 同一批跑两遍，去向相同 | 353 条里 344 条 |
| 两遍都判为新事件的，类型相同 | 27 条里 26 条 |
| 两遍都判为挂靠的，挂到同一事件 | 16 条里 16 条 |

试验暴露并已在本设计中处理的问题：行动者和报道者混淆、“做了什么”被套到所有类型上、转述被当成新事件、空泛的使用感受被留下、挂靠角色判不出来。

仍存在的问题：约 3% 的边界帖子两次运行结果不同；个别转述帖仍会被当成新事件。用户决定每批只跑一次，因此这部分误差会进入数据。

## 4. 每条帖子的三种去向

提取器对每条候选帖子给出一个去向：

| 去向 | 条件 | 结果 |
| --- | --- | --- |
| 新事件 | 帖子自己陈述了一件发生的事，且不在已知事件列表里 | 写入一条事件，帖子是它的来源 |
| 挂靠 | 帖子对已知事件列表里的某一个事件说了实质内容 | 写入一条挂靠记录：帖子、事件、补充了什么、原文引用 |
| 丢弃 | 其余 | 只在提取归档里记录丢弃原因，不写入事件相关的表 |

候选帖子是采集运行里已启用账号的原创帖，不含回复和转发，和现在相同，只是不再限于官方账号。

已知事件列表是近 30 天内的事件，不含活动公告，以编号、日期、公司、标题的形式放进提示词。30 天是规则参数，写在 schema 的规则里。

### 转述

转述别人消息的帖子不产生新事件。被转述的事在已知事件列表里、且帖子补充了具体细节的，挂靠；否则丢弃，丢弃原因以 `relay:` 开头，便于统计。

新事件只有两种来源：账号发布它自己的东西；作者自己第一手的使用、测试或测量。

## 5. 事件的表达

一句话：谁，用什么或关于什么，依据是什么；对部分类型再加上做了什么事、结果如何。

### 5.1 行动者

因为转述不算，新事件的行动者总是发帖账号的归属方。所以行动者不由模型填写，由程序从来源账号得到。

- 新增属性 `Event.actor_account_key`，指向来源账号。
- 账号归属于注册表里的公司时，照旧填 `primary_org_id`。
- 个人账号代表其所属机构发布时，模型可以给出机构名；程序只在这个机构与该人物的任职记录相符时采用，否则行动者就是这个人。
- 数据库约束“新词表下的事件必须有公司”改为“必须有行动者账号”。

### 5.2 新增属性

| 属性 | 含义 | 适用类型 |
| --- | --- | --- |
| `Event.subject` | 帖子里写的产品或模型名，原样记录 | 全部 |
| `Event.basis` | 依据，受控词表，见 5.4 | 全部 |
| `Event.task` | 一句话说明让 AI 做了什么具体的事，非工程师也看得懂 | 使用实录、独立测评、失败报告、生产采用 |
| `Event.result` | 结果，受控词表：成功、部分成功、失败、未说明 | 同上 |
| `Event.quote` | 陈述这件事的原文句子 | 全部 |
| `Event.schema_version` | 这条事件按哪一版 schema 提取 | 全部 |

`subject_key` 保留，继续用于去重和模型识别。产品作为独立的类不在这一版里。

### 5.3 事实

新增类 `EventFact`，一条事件可以有多条：数值、单位、指什么、原文引用、出自哪条帖子。帖子里给出的每个数字、价格、限制、成绩、日期、适用范围都记一条。

程序校验原文引用确实出现在帖子正文里，对不上的事实不入库。

### 5.4 词表

`event_kind` 从 2.0.0 升到 2.1.0，增加三项：

| 类型 | 定义 |
| --- | --- |
| `usage_report` 使用实录 | 具名的人或机构用 AI 产品完成一件具体的事，并说明结果 |
| `independent_evaluation` 独立测评 | 厂商以外的人测试或测量 AI 产品并报告结果 |
| `failure_report` 失败报告 | 有人报告 AI 产品在一件具体的事上失败或做不到 |

三项都要求有具体的事。“用了一整天”“感觉更好”属于观点，丢弃。个人或小团队发布自己的工具，归入已有的产品首发、版本发布、能力更新，但帖子要写出至少一项具体功能或一个数字。

新增词表 `event_basis`：

| 取值 | 含义 |
| --- | --- |
| `vendor_claim` | 出品方自己说的，没有他人测量 |
| `demonstration` | 给出了示例或演示，不是测量 |
| `own_use` | 报道者自己用过 |
| `measurement` | 出品方以外的人做的测试或基准 |
| `production_use` | 具名机构在真实业务中运行 |

新增词表 `event_result`：`succeeded`、`partly`、`failed`、`not_stated`。

### 5.5 关系

- 新增关系 `attached_to`：帖子挂靠到事件，带“补充了什么”和原文引用，不带角色。
- `announced_by`（事件到公司）保留；新增 `acted_by`（事件到来源账号）。
- 事件之间的关系、事件到公司的多方角色，不在这一版里。

## 6. 增量生效的版本规则

写入 `datasets/ontology/VERSIONING.md`，并由检查程序强制：

1. 每条事件记录提取时的 schema 版本。事件按哪一版提取，就按那一版解读。
2. schema 里的类、属性、关系、词表项可以写 `since`（从哪一版开始有）和 `until`（到哪一版为止）。没有 `since` 的视为一直存在。
3. 失效不删除：定义留在 schema 里并标 `until`；旧数据上的值原样保留；新提取不再写。
4. 新增不补旧：新属性在旧事件上是空值，含义是“当时没有记录”。
5. 默认不重抽。确需重抽某一批时，身份相同的事件（同一 `event_id`）在原行上升级到新版本：补上新属性，`schema_version` 改为新版本。升级前的内容保留在当时的提取归档里，归档不可覆盖。

本体版本从 2.1.0 升到 2.2.0（兼容增加）。现有 839 条事件不改动，`schema_version` 为空，表示早于 2.2.0。

### 词表标记不能再用等值比较

代码里有 26 处用 `kind_vocabulary = 'event_kind-2.0.0'` 筛选事件。词表升到 2.1.0 后，如果只是把这个常量改掉，旧的 839 条事件会从关联、验证、路由、发布里全部消失。

改法：这些地方改为“属于 `event_kind` 2.x 这一系”，由一个函数给出当前认可的标记集合。旧的 `legacy-freeform` 仍然排除在外。

这个标记还写在迁移 006 的数据库约束、生成的 SQL、投影构建脚本和判定哈希里。项目规则原文是“事件类型词表保持 2.0.0，本体升版本时它的行标记和判定哈希不得移动”。这次不是本体升版本带动的，而是词表自己加了三项，按版本规则应当升；但它会让判定哈希改变，新旧提取在哈希上不再相同。这是一次需要用户明确同意的变更，见第 11 节。

## 7. 存储

一个新迁移：

- `extracted_events` 增加列：`actor_account_key`、`subject`、`basis`、`task`、`result`、`quote`、`schema_version`，都可为空。
- `kind`、`basis`、`result` 的取值约束由 schema 生成，沿用现有的生成和比对机制。
- “必须有公司”的约束放宽为：2.0.0 的行必须有公司，2.1.0 的行必须有行动者账号。
- 新表 `extracted_event_facts`：事件、序号、数值、单位、指什么、原文引用、来源帖子。
- 新表 `extracted_event_attachments`：事件、帖子、补充了什么、原文引用、提取运行。

提取归档格式升到 `event-extraction-3`，多记录每条帖子的去向和丢弃原因。旧归档仍可重新入库。

## 8. 管线

- `pnpm data:extract:events` 增加账号范围选项：官方、名单、全部。提示词由 schema 生成，和现在一样。
- 一次提取同时处理新事件、挂靠、丢弃。
- 帖子与事件的关联表 `event_posts` 是每次全量重算的；重算时把挂靠记录作为一种新的关联方式 `attached` 并入。
- 模型识别照旧运行在所有事件上。
- **路由和进度只处理公司行动者的事件。** 人物和名单机构产生的事件暂不进入“佐证工作”和进度读数。原因：现有证据规则要求个人账号有自己的身份核查，而判断层是用户决定暂不动的部分。

## 9. 发布

- `sources.json` 里每个账号的 `latest` 改为：只放产生了事件或挂靠到事件上的帖子，仍取最近 3 条。没有这类帖子的账号 `latest` 为空。
- 只靠结构关系或提名匹配挂到事件上的帖子，内容没有被读过，不再发布。
- `events.json` 的范围暂不变：只含公司行动者的事件，但带上新属性和事实。人物产生的事件已在库里，是否上时间线另行决定。

## 10. 实施顺序

1. 版本规则和 schema：`since`/`until`、新属性、新类、新词表、`event_kind` 2.1.0；检查程序。
2. 把 26 处词表等值比较改为按系筛选，先保证旧事件不受影响。
3. 迁移和提取：新提示词、三种去向、事实校验、归档格式、入库。
4. 关联表并入挂靠；发布只放有事件的人物帖子。
5. 封存 2.2.0；`pnpm check`、`pnpm data:test`、`pnpm data:simulate`。
6. 用下一次日常采集作为新形态的第一批。

每一步都先写测试。

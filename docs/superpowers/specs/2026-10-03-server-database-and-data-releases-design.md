# 服务器数据库与数据发布设计

日期：2026-10-03。状态：用户已确认方向并要求立即实施；本文记录设计。它取代 [SEO、GEO 与部署设计](2026-10-03-seo-geo-deployment-design.md) 中"数据不离开本机、全站预生成"的部分，其余（语言地址、SEO、GEO、容器与候选/正式切换）继续有效。

## 用户的决定（2026-10-03）

1. 不采用"只上传成品页面"的方式。服务器上要有数据库，新数据以增量方式导入，按一个正常系统来部署。
2. 服务器数据库只放处理好、要展示的数据。采集和处理仍在本机运行（X 登录状态和代理在本机），原始抓取档案不上服务器。
3. 清洗好的库按版本管理，参照知识图谱数据的做法，保证不影响以后的用户数据。
4. 发布分为两条线：**发布代码**和**发布数据**。
5. 数据库版做好之前不上线静态版本。
6. 对外流量走服务器上现有的 Cloudflare Tunnel，不装 Caddy。

这改变了项目规则里"一期不做发布流程和上传器"的边界；`CLAUDE.md` 同步更新。

其余内容是本文提出的设计。

## 两类数据

| | 知识数据 `kg` | 用户数据 `app`（以后） |
| --- | --- | --- |
| 内容 | 已发布的事件、证据、工作等级、关卡、赛道、职业、人物与账号、模型、进度 | 账号、API Key、Agent 上报 |
| 写入者 | 只有本机发起的数据发布 | 线上实时写入 |
| 变化方式 | 按版本追加，不就地修改 | 正常增删改 |
| 数据库角色 | `oaw_kg_writer` 可写；网站用的 `oaw_site` 只读 | 以后单独的角色 |

`app` 这次不建。它以后只通过稳定标识引用知识数据（`kg.entities`），数据发布永远不写 `app`。

## 知识数据的版本模型

"要展示的数据"就是 `publish.build()` 已经算出的那一份（现在写成 `datasets/published/latest/` 的八个文件）。数据发布把这一份按行存进数据库，每次发布是一个不可变的版本。

- **`kg.releases`**：每个版本一行。版本号 `<生成时间 UTC>-<内容哈希前 8 位>`，带清单、内容哈希、状态（`loading` → `verified`）。
- **`kg.docs`**：按内容寻址的行内容（`sha256` → `jsonb`），只追加。同样内容的行在所有版本间只存一次。**这就是增量**：一次发布只写入新增或变化的行。
- **`kg.release_rows`**：版本的成员表。某版本的某个集合里，第几行是哪条内容（`release_seq, collection, ord, entity_id, sha256`）。
- **`kg.entities`**：出现过的实体标识登记表（`collection, entity_id, first_release_seq`），只增不删。以后用户数据的外键指向这里，版本切换不会让引用失效。
- **`kg.activations`**：生效记录，只追加。最新一条指向的版本就是当前生效版本。回滚是再追加一条指向上一个版本的记录。

集合与实体标识：`chain.activities`（`activity_id`）、`chain.gates`（`gate_id`）、`chain.events`（`event_id`）、`chain.evidence`、`chain.gate_edges`、`markets`、`tasks`、`events`（`event_id`）、`models`（模型标识）、`sources`（账号标识）、`coverage`、`progress`。没有天然标识的集合 `entity_id` 为空。

不为每个属性建列：实体的属性定义只在本体的 `schema.json` 里，数据库存的是符合它的文档。这遵守"类型和属性只定义一次"的规则。

导入在一个事务里完成：写入版本行（`loading`）、内容、成员、实体登记；然后从数据库把整份数据重新拼出来，按现有的规范化哈希算法重算，与清单的 `content_sha256` 相等才标为 `verified`。同一内容重复发布是空操作。只有 `verified` 的版本可以生效。

## 发布数据

在本机运行，经 SSH 转发连接服务器数据库（数据库只绑定服务器本机端口）：

| 命令 | 作用 |
| --- | --- |
| `pnpm data:release` | 把本地当前快照导入服务器，成为一个 `verified` 版本，不生效。打印与当前生效版本相比各集合新增、变化、移除的行数 |
| `pnpm data:promote` | 让最新的 `verified` 版本生效。网站在 30 秒内自动读到，不需要重新发布代码 |
| `pnpm data:rollback` | 让上一个生效过的版本重新生效 |
| `pnpm data:status` | 列出版本、当前生效版本、网站实际加载的版本 |

`--target local` 把同样的流程作用于本机 PostgreSQL，用于开发和测试。

数据流：本机管线 → `pnpm data:publish:snapshot`（不变）→ `pnpm data:release` → `pnpm data:promote`。

## 网站读数据

- 服务启动时从数据库加载当前生效版本到内存，加载完成才开始接受请求；之后每 30 秒查一次生效指针，变了就加载新版本并整体替换。
- 数据库在启动时不可用：服务启动失败，候选检查不通过，不会被切到正式。运行中数据库不可用：继续用内存里已加载的版本。
- 页面改为按请求渲染，不再在构建时预生成。不存在的地址由页面查不到数据后返回 404。
- 数据来源由环境决定：有 `DATABASE_URL` 读数据库；没有而本地有快照文件时读文件（开发、测试、CI）；都没有时显示"暂无数据"。
- `/healthz` 返回代码版本和已加载的数据版本。

## 发布代码

沿用已有的 `pnpm site:release`（候选，8321）和 `pnpm site:promote`（正式，8320）、`site:rollback`，变化：

- 构建不再读取数据，发布目录从约 550 MB 降到几十 MB。
- 版本号改为 `<构建时间 UTC>-<Git 提交>`。
- 网站容器加入与数据库相同的 Docker 网络，从服务器上的环境文件取得只读连接串。
- 候选检查读的是服务器数据库里当前生效的数据版本，所以首次上线的顺序是：建库 → 发布数据并生效 → 发布代码。

## 服务器上的数据库

- 一个独立的 Compose 项目 `openaiwill-db`：`postgres:16-alpine`，命名卷，只绑定 `127.0.0.1:5434`，加入 Docker 网络 `openaiwill`。
- `pnpm db:setup`（一次性，可重复执行）：建目录、生成口令并写入服务器上权限为 600 的环境文件、启动数据库、建库和两个角色、应用 `kg` 结构。口令不进 Git，也不存在本机；数据发布时经 SSH 读取。
- 备份：知识数据可以从本机重新发布；用户数据出现之前不设定时备份。手册里给出手动 `pg_dump` 的方法。

## 首次上线顺序

1. `pnpm db:setup`
2. `pnpm data:release`，然后 `pnpm data:promote`
3. `pnpm site:release`（候选读到真实数据并通过检查），然后 `pnpm site:promote`
4. 公网检查，通知搜索引擎

## 验证

- 数据：导入后重拼数据的哈希等于清单；重复导入是空操作；回滚后网站加载的版本随之改变。针对本机 PostgreSQL 的真实数据库测试。
- 网站：原有的输出测试改为对一个运行中的服务发请求；候选和本地冒烟检查不变（地址、跳转、404、站点地图、`llms.txt`）。
- `pnpm check` 全部通过；没有数据库也没有快照时构建和测试仍然通过。

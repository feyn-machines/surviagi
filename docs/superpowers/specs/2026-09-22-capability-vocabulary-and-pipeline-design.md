## 一、根因：46 个能力里 41 个不是能力

站内能力分两批，行为相差 19 倍：

| 来源 | 数量 | 中位命中职业 | 中位命中任务 |
| --- | ---: | ---: | ---: |
| 人工评审，从真实 AI 证据推出 | 5 | **25** | **49** |
| 自动发现，从 O*NET 任务文本推出 | 41 | **486** | **1,201** |

那 41 个是**工作的属性**——细节关注、问题解决、协调、信息综合。
它们描述任何一份白领工作，匹配一切，区分不了任何东西。
能力发现问错了问题：问的是「这项工作需要什么」，不是「AI 必须能做到什么」。

### 1.1 一个根因，五个症状

| 症状 | 机制 |
| --- | --- |
| 行李搬运员 17 项任务里 10 项被判「AI 做完人复核」 | 「协助旅客」匹配到 `customer-communication`（828 职业） |
| 软件开发 0% | 任务匹配到 `needs-assessment`、`interviewing`——无 AI 证据的工作属性 |
| 需要「宽度规则」打补丁 | 在给工作属性打补丁，而不是不把它们当能力 |
| 96 万次笛卡尔积 | 19,452 工作 × 46 能力，其中 41 个是噪声 |
| 换任何路由都省不下来 | 命中 923 职业的能力，怎么走都要走遍整棵树 |

三种路由的实测调用数同量级，**没有一种赢**：笛卡尔积 77,808 / 按能力收窄 21,405 /
按事件收窄 49,353。**次数不对是症状，词表不对是病。**

### 1.2 模拟：OpenAI 发布 Astra for Law

真实事件（2026-09-17，`product_launch`）跑通现有管线：

```
demonstrates  判了 158 次，判为「是」0 次
证据           0 条
进入图谱       没有
```

判官被逐个问的是「这条更新是否证明了 `surface-preparation`（表面处理）？
`clinical-observation`（临床观察）？」——**46 个能力里没有一个是法律工作。**

同一周，GitHub 一位法务用 Copilot 搭的内部小工具产生了 **3 条证据**，
因为它匹配上了 `ui-code-generation`（人工评审那 5 个之一）。

> 旗舰法律产品在图谱里什么都没发生，个人内部工具推动了三条边。
> **信号与噪声正好反了。**

## 二、三层的真实关系

19,452 个 work 被切成**互不相交的两半**，两棵树彼此不知道对方存在：

```
                    work 19,452
          ┌──────────────┴──────────────┐
      614 个                        18,838 个
   origin=editorial_ai          origin=onet_projection
        │ has_work                     │ has_task
    赛道 265                       职业 923
        │ has_market                   │ has_occupation
    市场组 40                      SOC 大类 23

            重叠 = 0      614 + 18,838 = 19,452
```

同一件事在两边各有一份文本：

```
赛道「法律文书起草与校核」→  Check citations attachments and filing formats
                           Draft pleadings defenses and procedural applications
职业「法务助理」          →  Gather and analyze research data, such as statutes…
                           Call upon witnesses to testify at hearings.
```

**这就是为什么站上只有职业没有赛道：赛道那半边每个只有 2–5 条，算不出任何东西。**

### 2.1 角色分工

| 层 | 是什么 | 谁来定 | 用途 |
| --- | --- | --- | --- |
| 市场组 40 / 赛道 265 | 做什么活 | AI 编写 | **事件的落点** |
| 赛道work 614 | 活的具体内容 | AI 编写 | **枢纽**：事件落这里，L 级挂这里 |
| SOC 大类 23 / 职业 923 | 谁在做 | O*NET | 读者找自己 |
| 任务 18,838 | 具体的活 | O*NET 原文 | 进度的分母 |

**任务是唯一的真实底座，赛道和职业是它的两种索引。**

## 三、去掉能力层

### 3.1 赛道work 取代能力

新链路里没有能力的位置：

```
旧：事件 ──demonstrates──▶ 能力 ◀──requires── 工作
新：事件 ─────────────▶ 赛道work 614 ──corresponds_to──▶ O*NET 任务
```

那 614 条本来就在扮演能力的角色，而且更合适：

| | 46 个能力 | 614 条赛道work |
| --- | --- | --- |
| 粒度 | 41 个是工作属性 | 全部是「活」 |
| 归属 | 悬空 | 挂在赛道树上 |
| 可评审 | 十万条边 | 614 条对应关系 |

**`capabilities` 表与 `requires`、`demonstrates` 三样一起退出结论计算。**
既有的边保留在库里作为历史与召回索引，不参与任何数字。

### 3.2 `demonstrates` 被吸收

事件直接落到赛道work 并给出 L 级，这一次判断同时回答了「证明了什么」与「到第几级」。
不再需要单独的 demonstrates 边。剩下的是**证据记录**（事件 / 赛道work / 层级 / L / 理由），
那是一行数据，不是一次判断。

### 3.3 `blocked_by` 保留但瘦身

它回答另一个问题：**就算 AI 做得到，制度也不允许**——医师签字、支付授权、执业资格。
这些不随模型变强而解除，与能力无关，因此不能删。

但不需要 17,237 × 11 的全量扫描。闸门挂在 614 条赛道work 上：

```
17,237 次  →  614 次
```

挡住的是「活」而不是单条任务，语义也更准确。

## 四、判官与题型（实测确定）

### 4.1 用 Jev，不用对照模型

`noul` / `score` / `choice` 是 **TypeSafe Jev 的原生题型**；DeepSeek 是对照组
（代码原文：*the same decision from a general chat model, for comparison*）。
96 万次全量扫描由 DeepSeek 跑完，是因为 **TypeSafe 额度中途用尽**，不是判官选择。

A/B 实测：177,771 对双判一致率 97.5%，但分歧不对称——
DeepSeek 单方面判「是」3,732 条，TypeSafe 单方面判「是」715 条，约 **5:1**。
判官越松，映射时选中的越多：赛道分母被稀释、一个职业挂进十几个赛道。
这正是 41 个泛能力那个病的翻版。

**三条映射一律用 Jev，DeepSeek 只作抽样对照。** Jev 额度已探测可用。

### 4.2 不需要新题型：批量是非一次能问几百个

初稿提议新增 `multi_choice`，**实测证明不必要且更差**。Jev 的
`questions` 字典一次可以带数百个 `noul`，因此「一次调用问 N 个选项」
用现成能力就能做到：

| | 多选 | 批量是非（实测） |
| --- | --- | --- |
| 调用数 | 1 | **1** |
| 每项置信度 | 无 | **有**（0.98 / 0.96 / 0.84 / 0.66） |
| 明确否定 | 无 | **有**，未选中的留下记录 |
| 阈值事后可调 | 否 | **是** |

多选会丢掉置信度与否定证据，而这两样正是区分「判过且否」与「没考虑到」所必需的。

### 4.3 每次调用的问题数上限：874–903

二分实测（`state` 为一条赛道work，每问一个职业）：

```
  114 问 → 成功  1.2s
  565 问 → 成功  2.0s
  790 问 → 成功  2.5s
  846 问 → 成功  4.1s
  874 问 → 成功  2.5s
  903 问 → 失败  HTTP 400 max_tokens_exceeded
 1016 问 → 失败  同上
```

职业总数 1,016，**分两批即可**，不必先选 SOC 大类。

### 4.4 抽样验证：判官选得准

「法律文书起草与校核」对法律大类 8 个职业：

```
0.98  Lawyers                         律师
0.96  Paralegals and Legal Assistants  法务助理
0.84  Legal Support Workers            法律支持人员
0.66  Judicial Law Clerks              司法书记员
── 未选中：法官、仲裁员、产权审查员、法庭记录员
```

同一条活对生产制造大类 114 个职业：**全部排除**，符合预期。

## 五、完整管线

### 5.1 一次性建库

```
① 赛道 265 ──▶ 职业 1,016          批量是非        530 次
   每赛道 2 批（上限 874/次，职业 1,016 个），无需先选 SOC 大类

② 赛道work 614 ──▶ O*NET 任务       多选       614 次
   候选池被 ① 限定：3–8 个职业的任务 = 60–160 项，6–16k 字符

③ 赛道work 614 ──▶ 闸门 11          多选       614 次
                                  ──────────
                                  约 1,800–2,000 次
```

### 5.2 每天增量

```
事件抽取                                    ≈  5 次
事件 ──▶ 赛道work + L 级 + 证据层级          ≈ 20 次
                                          ────────
                                          ≈ 25 次/天
```

对比现在的 **98,075 次**（其中 requires + blocked_by 占 97%）。

### 5.2.1 断点：续跑只问新的

每个 pass 扫一份确定的主体清单——265 个赛道、614 个活动、581 个事件——每个主体问几百个
问题。重跑要不要重新付钱，取决于 pass 记得什么。最初它只记住它留下的边，于是「这个主体
有没有边」被当成了「它判过没有」。两者只在每个主体都留下点什么时才等价，而实测是反的：
325/581 个事件不指向任何活动，329/614 个活动不被任何闸门约束。按边续跑，这些主体每轮都
重问一次。

`judgment_checkpoints`（迁移 018/019）主键是 `(method_version, subject_id)`：

- **按方法而不是按运行。** 续跑真正要问的是「这个主体在我要用的方法下判过没有」。
  改方法即改 `method_version`，所有主体自动到期，不需要手工清任何缓存。
- **`kept` 允许为 0。** 这是这张表存在的理由：把「问过、什么都没留下」与「从没问过」
  分开，边表做不到。
- **判完才写，失败不写。** 批次失败的主体、以及层级读取失败（证据行没有 L 级、对聚合
  无贡献）的事件，都不写断点，下一轮重新问。要避免的不是多打一次判官，是在半个答案上
  把主体标成完成。

四轮已完成的建库/路由运行（164,332 + 356,734 次提问，failed_batches 全为 0）已回填；
`questions_asked` 留 NULL——当时只记了每轮总数，写 0 等于声称什么都没问。四个 pass 现在
续跑都返回 `run_id=None`、零判官调用。每天的增量是新事件 × 614 ≈ 1.2 万次提问。

### 5.3 L 级只算一次，其余全是算术

```
                    赛道work 的 L 级
                          │ corresponds_to
                    O*NET 任务的 L 级      ← 唯一需要判断的一层
                          │
        ┌─────────────────┼─────────────────┐
     赛道进度          职业进度           全局进度
                  全部是 SQL，0 次额外调用
```

实测演示（现有口径）：全局 34.6% / 法律大类 34.7% / 法务助理 33.3%，
三个数出自同一份任务级数据。

## 六、聚合口径

### 6.1 取最低 + 闸门硬封顶

一项任务需要多种活（实测平均 4.8 种）。AI 只要有一种做不到，这项任务就做不了。
任务等级取**所需活中的最低级**，被闸门阻塞的直接封顶。

| 口径 | ≥L3 的工作项 | 占比 |
| --- | ---: | ---: |
| 取最高（当前发布） | 6,737 | 35% |
| 取最低 | 507 | 3% |
| 取最低且无闸门阻塞 | **385** | **2%** |

**现在发布的 35% 是 17 倍的高估。**

### 6.2 三态，未知不等于零

实测 71% 的任务至少需要一种没有等级的活。因此分三态：

- **已评估**：所需活全部有等级 → 给 L 级
- **未知**：至少一种没有证据 → 标「未评估」，不计入分子也不计入分母
- **未触及**：没有任何更新触及 → L0，计入分母

### 6.3 刻度 L0–L5（用户确认 2026-09-22）

```
L0 无 · L1 辅助 · L2 有人监督 · L3 人待命 · L4 限定范围无人 · L5 全场景无人
```

现有 0–4 一一映射到 L0–L4，不因改名重跑。L5 永远显示且当前为空——
「AI 接管世界的进度」自此字面成立：进度就是往 L5 走的距离。

### 6.4 跨赛道不可相加

赛道共用职业（法律秘书同属「法律文书起草」与「合同审查」）。
单个赛道的百分比正确，**相加会超过 100%**，页面不得出现「全赛道合计」。

两棵树就是封存的本体包 v1.0.0（`pnpm ontology:build` / `ontology:check`），

- 赛道目录本身 `origin=editorial_ai`，技术白皮书必须写明它不是行业统计口径。

## 十、风险

1. **赛道目录是 AI 编的**（305 个全部 `editorial_ai`，无权威出处）。
   粒度对，但来源弱，必须在技术白皮书里写明。
2. **614 条赛道work 无定义**（`definition` 为 null），只有标签。
   映射质量取决于标签是否足够自解释，第 ② 步跑完要抽样人工核对。
3. **取最低会让数字从 35% 掉到 2%**。这是修正不是退步，对外需要一次说明。
4. **判官一次的问题数有硬上限**（实测 874–903，超出返回 `max_tokens_exceeded`）。
   赛道work → 任务那一步的候选池若超过上限需分批，分批边界要记录进运行参数。
5. **L5 永远为空**可能被读成「没做完」。它是天花板，页面上要一直在。

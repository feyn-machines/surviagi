# SEO 与 GEO 策略

记录日期：2026-10-04。本文记录 openaiwill 在搜索引擎（SEO）和 AI 引擎（GEO，生成式引擎优化）上的定位、持续要做的事和改进顺序。技术实现见 [SEO、GEO 与部署设计](superpowers/specs/2026-10-03-seo-geo-deployment-design.md)，上线和发布流程见 [部署手册](development/deployment.md)。

文中区分三种内容：**用户已确认**的决定、**已实现**的现状、**提议**（尚未决定或尚未实现）。

## 定位

**"某个职业、某类工作，AI 现在实际能做到哪一步"的可引用出处，每个结论都能点回官方原始证据。**（提议，2026-10-04 与用户讨论，用户要求先记录）

这个位置目前没有人占：

| 现有内容 | 缺什么 |
| --- | --- |
| AI 新闻和模型测评 | 讲模型，不落到具体职业和任务 |
| "AI 会不会取代某职业"的观点文章 | 没有证据链，写完就过时 |
| 机构和大厂的研究报告 | 几个月一次，不能按职业逐条查 |

openaiwill 的三样独有资产：

- 职业拆到任务、赛道拆到工作的结构化目录。
- 每个等级（L0–L5）都挂着官方更新作为证据。
- 数据持续增量更新，按版本保存，可以回答"什么时候变的"。

定位建立在"结构化、有证据、持续更新"上。不靠替代百分比、失败概率或"已验证分数"吸引人，这是项目规则，也是与观点类内容的区别。openaiwill 是一项倡议，不称平台。

## 已实现的基础（2026-10-04 上线）

- 每种语言有独立地址；每页有 canonical、`hreflang`（en、zh-CN、x-default）、Open Graph 和 Twitter 卡片。
- `sitemap.xml`（约 3,400 个地址，带双语对应和更新时间）、`robots.txt`（点名允许 12 个 AI 爬虫）。
- 结构化数据：组织和网站、数据集（带版本、生成时间、"机器提出、未经审核"的状态）、面包屑、文章。
- `/llms.txt`：由站点导航、等级名称和数据清单生成。
- 关键数字在不执行脚本时也能读到。
- 数据发布与代码发布分开：新数据生效后网站约 30 秒内自动更新，不需要重新发布代码。
- 搜索引擎通知：`pnpm site:indexnow` 通过 IndexNow 协议向 Bing 等推送全部地址；Google 不支持该协议，靠站点地图和 Search Console。

## 改进顺序（提议）

按预期效果排序；第 1、2、6、7 项已实现，第 4 项按证据日期的版本和第 5 项的 Markdown 副本已实现，其余未实现：

1. **职业页和工作页顶部的"直接答案"行**：截止日期、多少项任务被 AI 更新触及、最高到哪一级。用标签加数字，不写解释性文字。AI 引擎倾向引用带日期、数字和来源的句子。（2026-10-16 已实现，未上线：工作页原已有；职业页和赛道页标题下加了一句，写法是“截至 {日期}，{职业}的 {n} 项任务中，AI 能做到 L2 及以上的有 {m} 项；有层级的共 {k} 项……”。日期是数据生成日期，数字与页面上的统计同源。）
2. **数据生效后自动通知搜索引擎，并且只推送新增和变化的页面**。差异在数据发布时已经算出。
3. **改详情页标题**：现在是"首席执行官 · 职业"这种形式，与实际搜索的说法对不上。文案需用户确定。
4. **变化历史页面**：某项工作的等级何时变化、依据是什么。依赖按版本保存的数据，是独有内容，也给爬虫回访的理由。（2026-10-16 按证据日期的版本已实现，未上线：工作页和它的 Markdown 副本有“它是怎么走到这里的”一节，按更新或帖子的日期列出最强证据每次升高的那一条，最后一行就是当前级别，并写一句“它在 {日期} 首次达到 L{n}”。工作级别等于名下最高的计入读数（含第三方印证），所以这段历史只用当前数据版本就能算出，不需要按版本存数据；它说的是证据发生的日期，不是本站采集或发布的日期。按数据版本记录“本站何时改了判断”仍未做。）
5. **给机器读的版本**：每页的 Markdown 副本、可下载的数据文件。（2026-10-16 Markdown 副本已实现，未上线；数据文件未做：工作页、赛道页、职业页在原地址后加 `/raw.md` 是同一内容的 Markdown，开头一句与页面上的直接答案逐字相同，链接都是完整地址，末尾写数据生成时间和“由机器提出、未经审核”。页面用 `rel="alternate" type="text/markdown"` 指向它；它用 HTTP `Link: rel="canonical"` 指回页面，让搜索引擎收录页面而不是副本；不收录的职业页，其副本也带 `noindex`。文章的 `raw.md` 也加了同样的 canonical。`llms.txt` 说明了这个地址规则。）
6. **优先推有证据的页面**：多数职业页尚无证据，内容偏薄；内部链接和站点地图优先指向有证据的页面。
7. **站点地图加短时缓存**：现在每次请求现场生成，约 4 秒。

## 2026-10-16 站点地图的更新时间（已实现，未上线）

此前除更新页外，每个详情页的 `lastmod` 都是数据生成时间，每次数据发布全部跳动，与页面是否真的变化无关；Google 只采用一贯准确的 `lastmod`。现在：

- 工作页取其证据中最新的更新发生时间；赛道页取其各项工作中最新的；职业页取服务它的各赛道中最新的；职业大类页取其各职业中最新的。与页面展示证据的连接方式一致。
- 话题页取最新一条说法的时间，更新页取更新发生时间（与此前相同）。
- 没有带日期证据的详情页不写 `lastmod`，不再用数据生成时间代替；列表页和首页概括整个版本，仍用数据生成时间。

这也是“改进顺序”第 2 项的前提：两次数据发布的站点地图之差，就是新增和变化的页面。

## 2026-10-16 数据发布只推送变化的地址（已实现，未上线）

此前只有代码发布（`pnpm site:promote`）会通知 IndexNow，而且每次推送站点地图里全部约 3,400 个地址；数据发布不通知。IndexNow 要求只提交新增、变化或删除的地址，反复提交未变化的地址会降低信任。现在：

- `pnpm data:promote`（和 `pnpm data:rollback`）在正式站确认读到新数据版本后，读取公开站点地图，与 IndexNow 上次接受的站点地图比较，只提交新增、`lastmod` 变化和已移除的地址。没有变化就不提交。
- 上次接受的站点地图记在本机 `data/indexnow/sitemap.json`（不进 Git）。本机还没有这份记录时，第一次提交全部地址。
- 代码发布仍然提交全部地址（页面模板可能全部变了），并更新这份记录。
- 判断依据是上一节按证据计算的 `lastmod`：一项工作有了新证据，它所在的赛道、职业和职业大类也随之变化，这些页面都会被提交；列表页和首页用数据生成时间，每次数据发布都会被提交。

## 文章栏目（2026-10-07 实现）

用户 2026-10-07 决定：做一个公开的文章栏目，不限于周报；标题写成“日期 + 一个主题”；文章按跨事件的几条线组织，每条线是几件具体的事加一句结论，最后一段直接写判断和猜测。

- **地址**：`/articles`、`/articles/<名称>`，中文在 `/zh-CN/articles/…`。导航里有“文章”。
- **来源**：`docs/articles/<名称>/en.md` 和 `zh-CN.md`，开头写 `title`、`description`、`date`；两种语言都有才出现。写 `draft: true` 的只在本机开发时可见。
- **发布方式**：文章页和白皮书一样在构建时生成，发布文章等于发布一次代码。站点地图和 `llms.txt` 按请求生成，读 `src/content/articles.json`（`pnpm articles:index` 生成，`pnpm i18n:test` 核对它与文档一致）。
- **给搜索和 AI 引擎的**：canonical、中英文互指、文章类结构化数据（带发布日期）、面包屑；进站点地图；每种语言一个 RSS（`/articles/feed.xml`）；每篇有 Markdown 副本（`/articles/<名称>/raw.md`），页面用 `rel="alternate"` 指向它和 RSS；`llms.txt` 列出每篇文章及其 Markdown 地址。
- **链接**：每个数字链到原帖；提到的更新链到站内对应的更新页。
- **判断**：文末“你”一段是当期的判断和猜测，文中标明不是数据；仍不写替代百分比、失败概率和“已验证”。

写作素材（2026-10-16 实现，只在本机）：`pnpm data:changes` 比较本机数据库里的两个数据版本（默认是上一个生效版本和当前生效版本；`--from`、`--to` 可以指定版本号或快照目录），在 `data/reports/changes-<旧>_<新>.md` 写一份中文素材：总数变化、等级变化的工作及其新证据、互动最高的新更新、同一主题的多条新更新（主题键前多写了公司名的，如 `openai-decisions-api`，并入 `decisions-api` 计数，不改更新本身）、各公司的新更新、新话题和说法增加的话题、新模型。它只读数据库，不连服务器；标题和问题保留原文，并注明全部由机器提出、未经审核。

未做：文章自动从数据生成（上面的素材只是输入）；向订阅名单发信；同步到其他平台。

## 2026-10-09 核心价值与持续发布（提议，讨论中）

用户 2026-10-09 提出：网站的核心价值理论上应该能持续发布和更新，现在做不到；并指出**热点也可以是持续发布的来源**。

对照数据（2026-10-08 快照和本地库）看到的现状：

- 每周进来 100–170 条更新，约 45% 触及具体工作。
- 614 类工作里 154 类有评级，其中 140 类只有厂商自述，按规则最高到 L2；到 L3 的 10 类。证据每天进来，等级几乎不动。
- 网站只显示当前状态，两次数据发布之间的差异没有页面。
- 个人的独立实测、使用报告和失败报告不参与评级，也没有落脚页，只出现在手写文章里。
- 不触及工作的那一半更新（模型发布、降价、上架）只有单条更新页，内容很薄。

提议把定位从“状态”改为“状态加变化”：**某类工作，AI 今天能做到哪一步；这周什么变了，谁试过，成没成。每一条都能点回原始出处。**

持续发布的单位是每次数据发布自动产生的页面，不是手写文章：

| 产出 | 来源 | 状态 |
| --- | --- | --- |
| 变化记录：哪类工作有了新证据、等级是否变化、哪个职业第一次被触及 | 两次数据发布的差异 | 未做 |
| 主题页和热点榜：一个模型、接口或产品一页，汇总发布、价格、谁试过、成没成、触及哪些工作；按近期帖子数和尝试数排出热点 | 更新的 `subject_key` | 未做 |
| 工作页上的“独立尝试”：几个人试过，几个成了，各自链接 | 个人的实测和使用报告 | 未做，见下方待定 |

热点的数据依据（2026-09-29 至 10-08，本地库）：343 件事里 341 件带主题，共 258 个主题。帖子最多的是 Qwen3.8-Flash-Next（32 件事、37 条帖子，28 次尝试成功）、Mistral Large 4（9 件事、28 条帖子）、Gemini 4 Argon、Decisions API、GPT-6.1 Sol（8 次尝试，3 成 4 未成）。同一主题目前会拆成几个键（如 `decisions-api` 与 `openai-decisions-api`），做主题页前要先合并。

每周文章由变化记录和热点榜汇总而来，人写最后一段判断。X 上每天发的内容也从这里取。

这一节取代上文“改进顺序”的排序：变化记录、主题页和热点榜排在最前，原第 3 项（改详情页标题）仍然有效，原第 4 项并入变化记录。

## 需要守住的规则

- 标题、描述、结构化数据、`llms.txt` 和文章都不出现替代百分比、失败概率或"已验证""已审核"的说法。
- 数据目前是机器提出、未经审核的。这个状态写给机器看（结构化数据、`llms.txt`），界面文案保持简短。
- 原始证据保持原语言，翻译单独标注。
- 每个结论链接到原始来源。

## 预期

- 新域名通常要几个月才有稳定的搜索流量，AI 引擎的引用一般更晚。
- 未经审核的状态会限制引用时的信任度；即使只有一小部分经人审核，也会是很强的可信度资产。
